Behind The reasoning

Most editors grew to hold your code. Snor is sized to hold your agents.

Supervising several coding agents is a different job from writing every line yourself, and it wants a different tool. This page is the reasoning behind the one that came out of it — including the parts deliberately left on the floor.

The problem

Agent-driven development quietly moves the hard part of the job. Writing a function is not the bottleneck any more; keeping four agents pointed at the right files, in the right directories, without one of them quietly undoing another's work, is.

The tooling did not follow. A typical session ends up spread across a terminal, an editor, a file explorer, a git client and several agent windows — and the switching cost lands squarely on the person doing the supervising. On a larger project, orchestrating the agents becomes as much work as the code they are writing.

The idea

Snor is an experiment in a calmer arrangement: one window holding the four things that matter while agents run — the project tree, the file, the shells, and a way to see all of them at once.

That ordering is deliberate. Flow Mode, where the window turns into live terminal panes, is the centre of the product, not a feature bolted onto an editor. The editor and the explorer exist to support it: the tree re-roots at whichever shell has focus, and any folder can spawn its own terminal. The point is to stop switching context every thirty seconds, not to match another editor keystroke for keystroke.

Getting to 155 MB

The size constraint came first, because it is the thing that makes the arrangement pleasant rather than merely possible. Four agent sessions on top of a heavyweight editor is a lot of memory to spend on supervision.

The first build was not small at all — ~331 MB in release with a 17 MB executable. Three changes did most of the work: switching to the glow rendering backend, stripping symbols, and enabling thin LTO. That took it to ~167 MB and a 12.5 MB exe. The rest came from keeping scope out.

VersionResult
V1 debug / release~306–313 MB / ~331 MB, 17 MB exe
V1.1 — glow, strip, thin LTO~173 MB / ~167 MB, 12.5 MB exe
Now~155 MB peak · ~147 MB commit · ~11 MB exe

One honest caveat sits on top of that number. It is a peak, not a level — Windows trims resident pages freely for a backgrounded window, so the same process can report 94.7 MB a minute later without anything having changed. Commit charge is the figure that stays put.

The full methodology is in the docs, including the PowerShell to reproduce it on your own machine.

What was left out

The scope decisions matter more than the feature list, and some of them are the reason the product is usable at all.

Not includedWhy
Extensions and a plugin systemA plugin API is a second product to maintain, and every plugin is somebody else's memory to pay for.
Git integrationA git client is a large surface area. That scope stays out so the memory figure stays down — use your own client beside it.
Accounts, sync and telemetryThere is nothing to log into and nothing to send. A dev tool should not phone home.
Cross-platform supportWindows first, honesty first. ConPTY is the terminal layer, so a port is real work rather than a recompile.
Multi-cursor power toolsSnor is not trying to replace a full editor. It covers the edits you make while supervising agents.
The rule of thumb: anything that would push the memory figure up has to earn its place by making agent supervision better. Most things do not.

Roadmap

  1. Stabilize the 1.0 workspace — editor, Flow Mode, terminal
  2. Signed release binaries on GitHub Releases
  3. Docs and screenshots
  4. Portability groundwork

Direction is set by use — by what actually helps supervise agents — not by feature parity with big editors. If a section of this page starts looking wrong in practice, it is the page that changes.
